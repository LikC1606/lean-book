# 第 15 章　工业级案例：AWS、Rust 与分布式协议

> 本章目标：了解 Lean 在工业界的三个标杆应用——Cedar（AWS 授权语言）、Aeneas（Rust 程序验证）、Veil（分布式协议验证），理解"验证驱动开发"如何落地到真实工程。

上一章的方法论是教科书式的。本章看工业界怎么用它解决**值真金白银**的问题。

## 15.1 Cedar：AWS 如何用 Lean 守住授权大门

### 问题

**Cedar** 是 AWS 开源的授权策略语言，驱动着 Amazon Verified Permissions、AWS Verified Access 等服务。它回答的问题形如：

> "用户 Alice 能否对资源 Photo123 执行 `delete` 操作？"

策略写错一个字，可能就是数据泄露或系统锁死。授权逻辑必须**绝对正确**。

### 做法：验证引导的开发（verification-guided development）

Cedar 团队的流程是 Lean 工业应用的经典模板：

```
┌─────────────────────── Lean 世界 ───────────────────────┐
│  1. 在 Lean 中实现 Cedar 的可执行模型（求值器、策略语言）   │
│  2. 在 Lean 中陈述并证明安全性质，例如：                   │
│     · "deny 策略永远胜过 permit"                         │
│     · "求值过程必然终止、类型安全"                         │
│     · "静态分析（验证器）报安全的策略，运行时不会越权"        │
└──────────────────────────────────────────────────────────┘
                          ⇅ 差分测试（海量随机用例对拍）
┌────────────────────── Rust 世界 ────────────────────────┐
│  3. 生产级 Rust 实现，与 Lean 模型逐行为对拍               │
└──────────────────────────────────────────────────────────┘
```

几个值得抄作业的细节：

- **模型即规范**：Lean 模型不仅是证明对象，还是团队的"可读规范"——比自然语言文档精确，比 Rust 代码易读；
- **对拍搭桥**：证明管不到 Rust 代码本身，于是用随机生成的海量策略 + 请求在两边同时对拍，让"Rust ≈ Lean 模型"的置信度逼近 1；
- **性质是真定理**：例如"deny 优先"（deny overrides）这类安全性质是在 Lean 内核里机械检查过的，不是代码评审的主观结论。

AWS 科学家公开评价：Lean 把"以前太复杂、不实际"的验证问题变成了日常工程实践。

## 15.2 Aeneas：把 Rust 搬进 Lean

### 问题

Rust 程序想验证功能正确性（不只是内存安全），传统做法要在验证器里模拟 Rust 的借用、所有权——推理极其痛苦。

### 做法：翻译，而非模拟

**Aeneas**（法国 Inria 与微软研究院等合作）的洞察很妙：

> Rust 的所有权系统已经保证了内存纪律，验证功能正确性时**根本不用谈内存**——把 Rust 函数翻译成 Lean 里的**纯函数**就行！

```
Rust 函数 ──Aeneas 翻译──▶ Lean 中的纯函数（+ 单调性定理）
                                  │
                                  ▼
                        在 Lean 中用普通定理证明技术
                        验证功能规格
```

于是验证 Rust 代码 ≈ 验证一个纯函数——回到第 14 章的舒适区。对panic/失败，Aeneas 生成 `Result` 风格的 monadic 代码；对循环，生成带不变量的递归。

**实战成果**：微软用 Aeneas + Lean 验证了 **SymCrypt**（微软的密码学库，服务于 Windows、Azure）中的生产级密码算法。密码学代码的正确性标准极苛刻（差之毫厘，安全性全毁），这是 Lean 验证能力的高难度背书。

### 为什么这对 Rust 社区意义重大

Rust 保证了"不会段错误"，但**保证不了"逻辑正确"**。Aeneas 补齐了这块拼图，让"经过功能验证的系统级代码"第一次变得实际可行。

## 15.3 Veil：分布式协议的多模态验证

### 问题

分布式协议（共识、复制、事务）是"最难写对"的软件类别：并发、网络延迟、节点故障交织出天文数字的执行路径，测试覆盖如同杯水车薪。Paxos、Raft 的正确性证明曾让无数专家掉头发。

### 做法：一个框架，多种验证武器

**Veil** 是嵌入在 Lean 中的分布式协议验证框架，设计理念是"多模态"：

```
协议描述（Veil DSL，嵌入 Lean）
    │
    ├──▶ 模型检查（有限实例上自动穷尽）
    ├──▶ SMT 自动化（一阶归纳不变量自动搜索）
    └──▶ 交互式证明（Lean 策略，处理自动化搞不定的引理）
```

关键卖点：

- **DSL 内嵌于 Lean**（第 19 章你会学到这门手艺）：协议写法接近论文伪代码，但每一行都有精确语义；
- **自动化优先，交互兜底**：简单不变量自动成立，真正需要人类智慧的归纳不变量才动用策略；
- **基础保证**：不同于独立的模型检查器，Veil 的所有结论最终由 Lean 内核背书——工具本身的 bug 不会污染正确性。

区块链共识、数据库复制的验证，正在从"专家专属"变成"工程师可及"。

## 15.4 更多信号：Lean 工业化的全景

- **FRO（Lean Focused Research Organization）**：非营利组织全职维护 Lean 核心，由 Simons 基金会、XTX Markets 等资助——基础设施级别的投入；
- **Harmonic**（Aristotle）：以 Lean 为底座的"数学超级智能"公司，目标行业包括航空航天、汽车、医疗——一切"安全攸关"的领域；
- **以太坊基金会**资助 ArkLib（下章细讲）；
- **NASA** 形式化方法研讨会把 Lean 列为重点方向；
- Quanta 出版《The Proof in the Code》——主流文化开始关注这场变革。

模式很清晰：**凡是"错的代价 >> 验证的成本"的领域，Lean 都在渗透。**

## 15.5 把经验带回家

工业案例给个人学习者的启示：

1. **模型先行**：哪怕不做完整验证，"用 Lean 写一个可执行的精确模型"本身就是顶级的设计文档；
2. **性质分级**：先证最值钱的不变量（钱守恒、权限不越界），别追求一次证完所有事；
3. **自动化 + 交互组合拳**：`grind`/`decide` 打头阵，策略收尾；
4. **对拍意识**：证明之外，让模型与实现互相印证，是性价比极高的工程实践。

## 15.6 本章小结

- **Cedar（AWS）**：Lean 模型 + 安全性质证明 + 与 Rust 实现对拍 = 生产级授权系统的形式化保障；
- **Aeneas**：把 Rust 翻译成 Lean 纯函数，绕过内存推理，已用于验证微软 SymCrypt 密码库；
- **Veil**：内嵌 Lean 的分布式协议验证框架，模型检查/SMT/交互证明三位一体；
- Lean 正沿着"错误代价最高的领域"（云、密码学、航天、金融）一路渗透。

## 练习

1. 阅读 Cedar 的 Lean 仓库（搜索 "cedar-spec"），找到"deny 优先"定理的陈述，读一读它如何用 Lean 语言表达安全性质；
2. 思考：你的日常工作中，哪个组件的"错误代价"最高？它的核心不变量用 Lean 怎么写？（写成 `theorem` 类型即可，不必证明）；
3. 用第 14 章的方法验证一个小型"权限系统"模型：
   ```lean
   inductive Action | read | write | delete
   structure Policy where allow : List Action; deny : List Action
   -- 证明：deny 列表中的动作永远不会被允许
   ```
4. （调研题）Aeneas 为什么能"不谈内存"？尝试用一句话向同事解释（提示：Rust 的所有权保证了什么，纯函数模型又丢掉了哪些信息）。
