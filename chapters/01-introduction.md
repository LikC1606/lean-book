# 第 1 章　初识 Lean 4：一门语言，两个世界

> 本章目标：搞清楚 Lean 到底是什么、能干什么、为什么值得你花时间。读完本章你不必能写出任何 Lean 代码，但你会清楚地知道"我接下来要学的是什么"。

## 1.1 从两个故事说起

### 故事一：四色定理的"信任危机"

1976 年，数学家阿佩尔和哈肯宣布证明了**四色定理**：任何地图只需要四种颜色就能保证相邻区域颜色不同。但这个证明引发了巨大争议——其中最关键的步骤是靠计算机枚举了上千种情况完成的。人类根本无法手工验证，那这个证明算不算数？

争议持续了几十年。直到 2005 年，数学家 Georges Gonthier 用定理证明器 Coq 把整个证明**完整形式化**了一遍——每一行推理都由机器检查。争议这才真正平息。

这件事给数学界提了一个问题：当一个证明长到没有任何一个人能通读它时，我们凭什么相信它？四色定理的答案是——**让一个可以被独立检查的小内核来代替人类审稿**。这个内核就是定理证明器的"心脏"，它的正确性是整个形式化方法的信任根基。

### 故事二：一个价值 5 亿美元的 bug

2016 年，以太坊上的智能合约 The DAO 因为一个代码漏洞被黑客卷走了价值约 5 亿美元的以太币。这个合约经过人类审计，但审计没有发现那个致命的**重入漏洞**（reentrancy）：攻击者利用合约在更新余额之前就转账的特性，反复触发提款函数，把账户掏空。

这种 bug 的共同特征是：**它不是某个变量写错、某行逻辑反了**，而是合约的"整体行为"和开发者的"心智模型"不一致——审计员一行一行读代码，每行都对，但合起来的语义是错的。

如果合约的正确性可以像四色定理那样被**机器验证**呢？如果我们在代码里写明"提款后余额必须减少"，并让机器证明"任何执行路径都满足这一点"呢？这类 bug 在形式化验证的视角下根本无处藏身。

### 两个故事的交汇

这两个故事指向同一个方向：**我们越来越依赖软件和数学，但人类检查错误的能力是有限的。** 我们需要机器来检查机器。

不是机器比人聪明，而是机器**不会偷懒、不会遗漏、不会"显然成立"地跳过**。Lean 就是把"让机器检查"这件事做得既严格、又可工程化的工具。

## 1.2 Lean 的"双重身份"

Lean 4 有两个身份，像一个硬币的两面：

**身份一：一门现代编程语言。**
你可以用 Lean 写普通程序——处理文件、解析 JSON、写命令行工具、写编译器。它是纯函数式的（类似 Haskell、OCaml），静态类型，编译到高效的本地代码。Lean 4 的编译器本身（超过 10 万行代码）就是用 Lean 4 写的。

**身份二：一个交互式定理证明器（ITP）。**
你可以在 Lean 里陈述数学命题，然后写出证明，Lean 的内核（kernel）会一步步检查你的证明是否**完全严格**——不留任何"显然"、"易证"的灰色地带。

更妙的是，这两个身份共享同一套语言、同一个编译器、同一个类型系统。这就是著名的**柯里-霍华德对应**（Curry-Howard correspondence）：

```
命题 = 类型
证明 = 程序
```

证明 `A → B`（A 蕴含 B），就是写一个类型为 `A → B` 的函数。这不是比喻，是 Lean 的实际工作原理。

让我们用一个能跑的小例子感受一下。在 Lean 里，"恒等函数"长这样：

```lean
def idNat (n : Nat) : Nat := n
```

而"恒等命题"——"任何自然数都等于它自己"——长这样：

```lean
theorem idNat' (n : Nat) : n = n := by rfl
```

两者结构完全一样：一个 `def`/`theorem`，一个名字，参数 `(n : Nat)`，一个结果类型，一个实现。区别只在于，`def` 的结果类型是"数据类型"（`Nat`），`theorem` 的结果类型是"命题类型"（`n = n`，这是一个 `Prop`）。在 Lean 看来，这俩没本质区别——**类型就是命题，构造这个类型的值就是证明它**。我们会在第 8 章详细展开这个对应。

这意味着一件很反直觉的事：**写 Lean 程序和写 Lean 证明用的是同一套技能**。你学会定义函数、用模式匹配、写递归，就同时学会了写证明的基本功；反过来，你训练出的"严格推理"思维，也会让你写的程序更可靠。这是 Lean 区别于"纯编程语言"和"纯证明器"的根本之处。

## 1.3 Lean 4 的版图：它正在改变世界的地方

让我们快速浏览 Lean 4 的真实应用版图——这也对应着本书的章节结构。

### 🔢 数学形式化（第 11–13 章）

**mathlib** 是 Lean 的社区数学库，目前已包含超过一百万行形式化数学，覆盖代数、分析、拓扑、数论、概率、组合……几乎涵盖本科到研究生阶段的全部主流数学。它由全球数百名贡献者协作维护，每周都在增长——可以说 mathlib 是目前人类最大的"机器可检查的数学知识库"。

- 2021 年，数学界震动：Lean 社区验证了 **完美准环面（perfectoid spaces）** 的定义——这是菲尔兹奖得主 Peter Scholze 的前沿研究对象，连他自己都惊讶于 Lean 能"消化"这么现代的概念（**Liquid Tensor Experiment**）。Scholze 在博客中写道：他第一次对证明中的某个技术引理"完全确信"，因为 Lean 检查了它。
- 帝国理工学院的 Kevin Buzzard 教授正领导一个宏大项目：把**费马大定理**的完整证明形式化进 Lean。这个项目预计耗时数年，但已经吸引了大量志愿者——它本身就是"AI 时代数学如何协作"的一个实验。
- 陶哲轩（Terence Tao）多次公开使用并推广 Lean，称它让大规模数学协作成为可能。他甚至在 Lean 里形式化了自己的若干研究内容，用于检验思路。

### 💻 软件验证（第 14–15 章）

- **AWS** 用 Lean 形式化验证了其授权策略语言 **Cedar**，该系统保护着 Amazon Verified Permissions 等生产服务。团队先在 Lean 中建可执行模型、证明安全性质（如"授权判定只依赖策略与请求，不会泄露跨租户信息"），再用差分测试把模型和生产代码对齐。他们公开了技术报告，是工业级 Lean 验证的标杆案例。
- **Aeneas** 项目把 Rust 代码自动翻译成 Lean 中的纯函数模型，从而绕开内存推理，直接验证 Rust 程序的功能正确性。微软用这条工具链验证了 SymCrypt 密码库中的生产级算法——这是密码学库首次被这样端到端验证。
- **Veil** 是一个嵌入在 Lean 里的分布式协议验证框架，用于验证区块链共识、数据库复制等"最难搞对"的系统。这类系统的 bug 往往只在极端并发与时序下出现，测试很难覆盖，形式化验证几乎是唯一靠谱的手段。

### 🔐 密码学与区块链（第 16 章）

**ArkLib**（以太坊基金会支持）正在用 Lean 形式化验证 **SNARK**（简洁非交互式知识论证）——这是零知识证明系统的核心，一个可靠性 bug 就可能造成灾难性后果：要么让虚假证明通过（资金被盗），要么让诚实用户被拒（服务中断）。Lean 给了这些密码学系统"机器检查过的安全证明"。这类验证比传统密码学论文的"安全性论证"严格得多——后者依赖人脑追踪几页的规约链，前者则是每一步都被内核检查。

### 🤖 AI 与自动定理证明（第 20 章）

- **AlphaProof**（Google DeepMind）：用强化学习 + Lean 形式化反馈训练出的数学推理系统，在 2024 年 IMO 题目上达到银牌水平。关键在于：Lean 提供了一个**零假阳性的奖励信号**——AI 生成的证明要么被 Lean 接受，要么不接受，没有"差不多对"。这是 RL 训练能跑起来的前提。
- **LeanDojo**、**REPL**、**Pantograph**：让机器学习模型可以程序化地与 Lean 交互的工具链，是"AI 数学家"研究的基础设施。你可以把 Lean 想成一个"永远在线、永远严格的数学老师"——AI 每走一步，它立刻告诉你对错。
- 数学基础模型公司 **Harmonic**（Aristotle）等直接用 Lean 作为验证底座，把"证明数学定理"做成了可商业化的 AI 能力。

### 🎓 教育（第 21 章）

- **自然数游戏**（Natural Number Game）：一个网页游戏，从定义自然数开始，一关一关教你用 Lean 证明加法交换律、乘法分配律……全球数万玩家通过它第一次体验了形式化证明。很多人形容它"像解谜游戏，上头"。
- Fordham 大学、帝国理工等高校已经把 Lean 引入本科数学课堂。学生反馈：用 Lean 之后，对"为什么这步成立"的理解反而比传统课堂更深——因为你**必须**把每一步写清楚。

### 🛠 编程语言与工具（第 4–7、17–19 章）

Lean 4 本身就是"自举"的：它的编译器、策略系统、宏系统全部用 Lean 4 编写。你也可以用 Lean 强大的元编程能力造自己的领域语言（DSL）——Lean 甚至有一整套写文档/写书的工具 **Verso**，Lean 官方文档就是用它生成的。这意味着：**学会 Lean，你就拥有了一把既能写程序、又能"改造编程语言本身"的瑞士军刀。**

## 1.4 Lean 与同类工具的对比

| 工具 | 定位 | 与 Lean 4 的差异 |
|------|------|------------------|
| **Coq / Rocq** | 老牌定理证明器 | 历史最久，四色定理、CompCert 编译器验证都基于它；Lean 4 语法更现代、元编程更强、编程体验更好 |
| **Isabelle** | 定理证明器 | 自动化很强（特别是 Sledgehammer）；Lean 社区增长更快，mathlib 生态更活跃 |
| **Agda** | 依赖类型语言 | 学术味浓，适合类型论研究；Lean 工程化更好、性能更高 |
| **F\*** | 验证导向语言 | 偏 SMT 自动化验证（Project Everest 用它验证 HTTPS 栈）；Lean 交互式证明能力更强、依赖类型更灵活 |
| **Dafny** | 验证感知编程 | 面向工业验证，语法接近常见语言，门槛低；Lean 表达力（依赖类型）更强，能做更深的数学 |
| **Haskell/OCaml** | 函数式语言 | 只是编程语言，无法做定理证明；Lean 在编程体验上接近它们，但多了证明能力 |

一句话总结：**Lean 4 在"强大的定理证明"和"实用的编程语言"之间取得了目前最好的平衡**，并且拥有增长最快、最活跃的社区。如果你只能在这十年里学一门形式化方法工具，目前 Lean 是性价比最高的选择。

需要诚实说明的是：Lean 不是银弹。对纯 SMT 风格的"自动验证小程序"任务，Dafny/F* 上手可能更快；对超大规模的传统数学定理库，Coq 的历史沉淀更深。Lean 的优势在于**通用性和生态势能**——同一门语言能从写脚本一路做到证明前沿数学。

## 1.5 Lean 的哲学：为什么"麻烦"是一种诚实

用过 Python、JavaScript 的人，初见 Lean 常常会觉得"太麻烦了"：写个递归还要证明它终止？没有 `null`？变量不能改？这背后是一种**深思熟虑的取舍**。

普通语言优先**方便**：能跑就行，错了再说。Lean 优先**确定**：如果你写了一个函数，Lean 想保证它**对所有输入都有唯一的、可计算的输出**——否则它没法在证明里被信任。这就要求：

- **没有副作用**：函数只依赖输入，不偷摸改全局状态，这样"`f 3` 永远等于 `f 3`"才成立；
- **没有部分函数**：函数不能"对某些输入算不出来"（像 Haskell 里臭名昭著的 `head []` 会崩溃），所以可能为空的情况要显式用 `Option`；
- **必须终止**：不然"结果"这个概念就不存在。

这些"麻烦"换来的是：**你可以用函数当证明的构件**。一个被 Lean 接受的 `def`，是一个数学上"绝对可靠"的积木。当这些积木搭成一个定理的证明时，整个证明的可靠性就追溯到那个小小的、被无数人审视过的内核。

这就是形式化方法的本质：**用"前期麻烦"换"后期绝对确信"**。在小程序、一次性脚本里这种取舍不划算；但在密码学库、共识协议、数学定理这些"错一次代价巨大"的领域，它物超所值。

## 1.6 学习 Lean 难吗？

诚实的回答：**入门不难，精通有挑战，但沿途风景极好。**

- 如果你有编程基础，第一周的体验会像学一门新颖的编程语言（想想第一次接触 Haskell 的感觉）；
- 如果你有数学基础，你会发现 Lean 强迫你把"显然"变成"严格"，这个过程会反过来加深你的数学理解；
- 最陡峭的部分通常是**依赖类型**（dependent types）和**策略证明**的思维转换——这正是本书要花大力气讲透的。

一个常见的心理障碍是"证明好抽象、不知道在干嘛"。破解方法是**永远盯着 Infoview**——它实时显示"我现在要证明什么、有哪些假设可用"，把抽象的推理变成可视的游戏面板。本书第 3 章和第 9 章会反复强调这一点。

学习建议：

1. **先玩自然数游戏**（https://adam.math.hhu.de/），2–3 天通关基础关卡，建立直觉；
2. **跟着本书敲代码**，每一个示例都亲手输入、运行、改一改；
3. **卡住是正常的**。Lean 社区（Zulip 聊天室）以友好著称，新手问题基本都会得到解答。

## 1.7 本章小结

- Lean 4 = 函数式编程语言 + 交互式定理证明器，两者共享同一类型系统；
- 核心思想是柯里-霍华德对应：**命题即类型，证明即程序**——`def` 和 `theorem` 在 Lean 里几乎是一回事；
- Lean 已在数学形式化（mathlib、Liquid Tensor Experiment、费马大定理）、工业软件验证（AWS Cedar、Aeneas、Veil）、密码学（ArkLib）、AI 定理证明（AlphaProof）、教育（自然数游戏）等领域产生真实影响；
- Lean 的"麻烦"（不可变、无 null、必须终止）是它"诚实"的代价，换来的是机器可检查的可靠性；
- 学习曲线前缓后陡，但社区友好、工具成熟，现在是入门的最好时机。

1. ⭐ 访问 [Lean 官网](https://lean-lang.org)，浏览 "Use Cases" 页面，挑一个你最感兴趣的案例读一读，用一句话总结它"为什么需要形式化"；

3. ⭐⭐ 思考题：为什么"机器检查证明"比"人类审稿"更可靠？它又有哪些局限？（提示：考虑内核本身的信任问题、形式化与现实语义的鸿沟）；
4. ⭐⭐ 思考题：找一个你听说过的著名软件 bug（如 Ariane 5 火箭、Therac-25 医疗辐射机、Intel Pentium FDIV 除法 bug），想想它属于"实现错误"还是"规格说明错误"——形式化验证对哪一类有效、对哪一类无效？
